# 开发规则（Dev Rules）

本文件是**跨功能开发规则的唯一权威汇总**：每条规则含编号、要求与说明；后续新增规则按编号追加（R4、R5…），不另开文档。AGENTS.md 通过指针引用本文件，agent 与开发者执行任务时必须遵守。

## R1 e2e 定位标注（data-testid）

**规则**：

1. 新增或修改**会话看板**的可交互 UI 元素（按钮、输入框、表格行、抽屉、提示条等）时，只要 e2e 测试需要定位它，就必须设置 `data-testid`；断言一律以 testid 定位，界面文案只作辅助断言——文案可随时改，testid 改动视为契约变更。
2. 同一次提交中必须同步更新 `tests/e2e/TESTIDS.md`（清单：testid → 组件文件 → 用途 → 关联用例）；改组件不改表、或改表不改组件，均视为遗漏。删除/重命名 testid 还须同步更新 `tests/e2e/` 下引用它的用例。
3. 命名与多元素标注、维护细则以 `tests/e2e/TESTIDS.md` 的「维护规则」为准（单一事实来源，本文不复制清单）。

**说明**：动机是把 UI 文案变化与测试资产解耦——没有 testid 时用例只能靠文案或结构定位，脆且需要反扫代码库。不必给纯展示、已有稳定 role/name 的元素加 testid。

## R2 e2e 执行纪律（正式执行只报告，不自动修复）

**规则**：

1. **正式执行**（对已入库的 e2e 资产、面向目标环境的验证运行）：失败时**只记录错误与原因，不自动修复**——不改业务代码、不改 e2e 脚本、不改目标环境来让用例通过。产出为**不入库的测试报告**（Playwright 报告/截图/trace 已在 `.gitignore`；结论与失败原因写在会话汇报中）+ 每条失败的**修复建议**，由人决定后续开发任务。
2. **脚本开发期**（新增/修改 e2e 脚本本身，并对脚本与目标功能做联调验证）：允许直接修改脚本与相关代码，验证通过后按提交规范入库。
3. 两者的分界：改动动机是"让 failing 的既有用例变绿且用例本身正确"——属于正式执行发现问题，走第 1 条；动机是"用例需要新增/修正以覆盖新功能或修正错误假设"——属于脚本开发期，走第 2 条。
4. 执行环境不可满足用例前提（缺 Chromium、目标不可达、造数失败等）时，按 `tests/e2e/` 的预检设计**明确报告并停止**，不得在运行时自动安装依赖或修改环境绕过。

**说明**：动机是把"测试发现的问题"与"测试自身的问题"分开处置，避免为绿而绿（改代码迁就错误用例，或改用例迁就缺陷）。

## R3 开发期版本与制品命名

**规则**：

1. **开发过程中**构建的制品（镜像、发布包等）版本号为 `<基础版本>-dev.<序号>`，序号取 `date +%g%V%u%H%M`（2位年 + 2位ISO周 + 1位周几(1=周一) + 4位时分，共 9 位），例如 `0.1.2-dev.264710300`（2026 第 47 周周一 03:00）。**同一次开发迭代内重跑允许覆盖同一 dev tag**；保留最近 1–2 个 dev tag 即可，更早的及时清理。
2. **只有发布时才变更制品版本号**（如 `0.1.3`、`0.1.3-dashcam`）：发布意味着 CHANGELOG、tag 与制品三者对齐；开发迭代一律停留在当前基础版本的 `-dev` 序号上，不得递增。
3. 发布制品对应的旧镜像/二进制按部署文档保留为回滚资产；`-dev` 制品不属于回滚资产，可随时清理。

**说明**：动机是把"开发迭代"与"正式发布"在命名层分开——开发期反复构建若递增版本号，会让版本号失去发布语义，且回滚资产清单被开发噪声污染。

## 规则扩展

新增规则直接在上方按编号追加小节并更新索引表；若某规则与仓库既有文档（如 `tests/e2e/README.md`、`TESTIDS.md`）有重叠，**以规则文档定义义务，以专项文档定义细节**，规则文档内用链接引用，不复制内容。
