# New API 用户使用量统计看板 · 最终方案（TypeScript + PostgreSQL 直连）

## 0. 方案定位

独立部署的 TypeScript 全栈看板，直连 New API 的 PostgreSQL 数据库，服务端完成 SQL 聚合与统计，前端负责可视化展示与导出。

核心原则：
- 只读数据库，使用只读账号，优先连接从库
- 不修改 New API 数据库 schema，不依赖不存在的导出接口
- 服务端聚合，前端只展示
- 不用 Python，不用 Redis（除非未来多实例部署）
- 缓存用进程内 lru-cache，容量上限 1GB，重点防慢泄漏
- 界面不追求与 New API 一致，走现代化 shadcn/ui + Tremor + ECharts 路线

## 2. 数据库对接

### 2.1 连接方式

- 使用只读账号连接 PostgreSQL
- 优先连接只读从库，避免影响主库写入
- 连接池上限建议 10–20

```env
DATABASE_URL=postgres://dashboard_readonly:password@db-host:5432/new_api
```

只读账号创建：

```sql
CREATE ROLE dashboard_readonly LOGIN PASSWORD 'your_password';
GRANT CONNECT ON DATABASE new_api TO dashboard_readonly;
GRANT USAGE ON SCHEMA public TO dashboard_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dashboard_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO dashboard_readonly;
```

### 2.2 核心表

| 表 | 用途 | 特点 |
|---|---|---|
| quota_data | 按小时聚合的用量数据 | 适合天/周/月汇总，有最多 5 分钟延迟 |
| logs | 原始消费日志 | 适合精确请求数、RPM/TPM |
| users | 用户基础信息 | 用户名、状态、额度 |

字段以实际 `\d quota_data`、`\d logs` 为准。常见字段：
- quota_data: user_id, username, model_name, created_at, token_used, quota, prompt_tokens, completion_tokens
- logs: user_id, username, created_at, model_name, quota, prompt_tokens, completion_tokens

### 2.3 保留策略确认

```sql
SELECT MIN(to_timestamp(created_at)), MAX(to_timestamp(created_at))
FROM quota_data;
```

如发现数据被清理，考虑从 logs 回填或建立独立归档表。

### 2.4 索引建议

若生产库不允许建索引，请在从库或独立看板库处理。

```sql
CREATE INDEX CONCURRENTLY idx_quota_data_created_at ON quota_data (created_at);
CREATE INDEX CONCURRENTLY idx_quota_data_user_created ON quota_data (user_id, created_at);
CREATE INDEX CONCURRENTLY idx_quota_data_model_created ON quota_data (model_name, created_at);
CREATE INDEX CONCURRENTLY idx_logs_created_at ON logs (created_at);
CREATE INDEX CONCURRENTLY idx_logs_user_created ON logs (user_id, created_at);
```

## 5. 核心 SQL（PostgreSQL）

### 5.1 全局总览

```sql
SELECT
  COALESCE(SUM(quota), 0) AS total_quota,
  COALESCE(SUM(token_used), 0) AS total_tokens,
  COALESCE(SUM(prompt_tokens), 0) AS prompt_tokens,
  COALESCE(SUM(completion_tokens), 0) AS completion_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2;
```

请求数从 logs 查：

```sql
SELECT COUNT(*) AS request_count
FROM logs
WHERE created_at >= $1 AND created_at < $2;
```

### 5.2 按天趋势

```sql
SELECT
  DATE_TRUNC('day', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS day,
  SUM(quota) AS total_quota,
  SUM(token_used) AS total_tokens,
  SUM(prompt_tokens) AS prompt_tokens,
  SUM(completion_tokens) AS completion_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY 1
ORDER BY 1;
```

### 5.3 按周趋势

```sql
SELECT
  DATE_TRUNC('week', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS week,
  SUM(quota) AS total_quota,
  SUM(token_used) AS total_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY 1
ORDER BY 1;
```

### 5.4 按月趋势

```sql
SELECT
  DATE_TRUNC('month', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS month,
  SUM(quota) AS total_quota,
  SUM(token_used) AS total_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY 1
ORDER BY 1;
```

### 5.5 单用户按天趋势

```sql
SELECT
  DATE_TRUNC('day', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS day,
  SUM(quota) AS total_quota,
  SUM(token_used) AS total_tokens
FROM quota_data
WHERE user_id = $1
  AND created_at >= $2 AND created_at < $3
GROUP BY 1
ORDER BY 1;
```

### 5.6 单用户模型分布

```sql
SELECT
  model_name,
  SUM(quota) AS total_quota,
  SUM(token_used) AS total_tokens,
  SUM(prompt_tokens) AS prompt_tokens,
  SUM(completion_tokens) AS completion_tokens
FROM quota_data
WHERE user_id = $1
  AND created_at >= $2 AND created_at < $3
GROUP BY model_name
ORDER BY total_quota DESC;
```

### 5.7 用户消耗排行

```sql
SELECT
  user_id,
  username,
  SUM(quota) AS total_quota,
  SUM(token_used) AS total_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY user_id, username
ORDER BY total_quota DESC
LIMIT $3;
```

### 5.8 最近 1 小时 RPM

```sql
SELECT
  DATE_TRUNC('minute', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS minute,
  COUNT(*) AS requests
FROM logs
WHERE created_at >= EXTRACT(EPOCH FROM NOW())::bigint - 3600
GROUP BY 1
ORDER BY 1;
```

## 6. 缓存方案（重点）

### 6.1 选型

使用 `lru-cache`，进程内缓存，不引入 Redis。

容量上限 1GB，重点关注慢泄漏问题。

### 6.2 配置

```ts
import { LRUCache } from 'lru-cache';

const CACHE_MAX_SIZE = 1024 * 1024 * 1024; // 1GB

const cache = new LRUCache<string, unknown>({
  maxSize: CACHE_MAX_SIZE,
  ttl: 60 * 1000,
  ttlAutopurge: true,          // 定期清理过期条目
  updateAgeOnGet: false,       // 读取不刷新 TTL，避免热点永不过期
  sizeCalculation: (value) => {
    // 精确估算序列化后的字节数
    return Buffer.byteLength(JSON.stringify(value), 'utf8');
  },
  dispose: (value, key, reason) => {
    // 可选：记录淘汰原因，便于排查慢泄漏
    if (process.env.NODE_ENV === 'development') {
      console.debug(`[cache] evict ${key} reason=${reason}`);
    }
  },
});
```

### 6.3 防慢泄漏的关键措施

慢泄漏的典型来源：TTL 不生效、热点数据永不过期、缓存 key 无限增长、value 引用外部大对象、异步写入未清理。

针对性措施：

**（1）强制 TTL 生效**
- 每条缓存必须设置 TTL，不允许 `ttl: 0`（永不过期）
- 使用 `ttlAutopurge: true` 定期清理
- 使用 `updateAgeOnGet: false`，避免热点数据被反复访问而永不过期

**（2）严格控制 key 数量**
- key 必须由查询参数确定性生成，如 `${granularity}:${start}:${end}:${userId ?? 'all'}`
- 参数做规范化（时间戳取整到秒、userId 转字符串），避免同一查询产生多个 key
- 对用户输入的 modelName、groupId 等做白名单或长度限制

**（3）按维度分级 TTL**

| 数据 | TTL | 理由 |
|---|---|---|
| 全局总览 | 60 秒 | 热点，变化不频繁 |
| 用户排行 | 120 秒 | 查询重，变化慢 |
| 单用户趋势 | 30 秒 | 命中率一般 |
| 模型分布 | 30 秒 | 命中率一般 |
| 实时 RPM | 10 秒 | 接近实时 |
| 历史月度汇总 | 1 小时 | 数据不变 |

**（4）定期监控与主动清理**

```ts
// 每 5 分钟输出一次缓存统计，便于观察是否增长异常
setInterval(() => {
  console.log('[cache]', {
    size: cache.size,
    calculatedSize: cache.calculatedSize,
    maxSize: CACHE_MAX_SIZE,
  });
}, 5 * 60 * 1000);
```

当 `calculatedSize` 长期接近上限时，说明缓存压力大或存在泄漏，需要检查 key 生成逻辑和 TTL 配置。

**（5）慢泄漏兜底**

- 使用 `cache.purge()` 在进程收到 SIGTERM 时主动清空
- 提供 `/api/admin/cache/clear` 管理端点（加访问控制），手动清空缓存
- 使用 `cache.delete(key)` 在数据变更时主动失效（看板为只读，通常不需要）

### 6.4 内存评估

缓存内容是聚合后的查询结果，不是原始日志：
- 按天返回一年：365 条 × 约 500 字节 ≈ 180 KB
- 用户排行 Top 100：约 30 KB
- 单用户详情：约 50–200 KB

即便有 1000 个不同查询同时命中缓存，总占用通常也在 100–300 MB 之间，1GB 上限有充足余量。若长期逼近上限，说明 key 生成或 TTL 有问题，应优先排查而不是继续扩大上限。

### 6.5 何时不缓存

若单次聚合查询在合理索引下耗时 < 100ms，可以直接不缓存。用 SQL 优化和索引替代缓存，是最省内存的做法。

## 8. 静态 HTML 快照导出

### 8.1 前端单图导出

口径修订（2026-10-09 回流批准）：ECharts 并无 `exportToHTML` API（5.6 / 6.1 均已核验），改为「自包含 HTML 模板 + `getOption()` 序列化 + echarts 运行时内联」。

```ts
const option = chart.getOption();

const html = renderSingleChartHtml({
  title: 'user-report',
  option,            // getOption() 序列化后的图表配置
  echartsSource,     // 内联 echarts 运行时（取本地产物，不依赖外网 CDN）
});

saveAs(new Blob([html], { type: 'text/html' }), 'user-report.html');
```

导出后打开仍保留 tooltip、图例筛选、缩放等交互（依赖内联的运行时与 option）；暗色 option 按当前页面主题内联生成。

### 8.2 服务端完整看板快照

使用 Playwright：

```ts
import { chromium } from 'playwright';
import fs from 'node:fs/promises';

const browser = await chromium.launch();
const page = await browser.newPage();
await page.goto('http://localhost:3000/users/123?start=...&end=...');
await page.waitForLoadState('networkidle');
const html = await page.content();
await fs.writeFile('snapshot.html', html);
await browser.close();
```

可定时生成日报、周报、月报快照，归档到 data/snapshots。

口径修订（2026-11-11 回流批准）：快照改为写入非公开目录 `data/snapshots`（容器内由 `SNAPSHOT_DIR` 指定），读取经受 Basic Auth 保护的 `GET /api/snapshots/[file]` 路由（文件名白名单防穿越）；不再放入 `public/` 静态目录，落实 §11.2「快照目录单独加访问密码」。

### 8.3 快照内容建议

- 全局总览
- 单用户报告
- 月度报表
- 模型分析报告
