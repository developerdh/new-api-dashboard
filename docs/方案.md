# New API 用户使用量统计看板 · 技术方案

## 0. 方案定位

独立部署的 TypeScript 全栈看板，只读直连 New API 的 PostgreSQL 数据库。服务端完成 SQL 聚合与统计，前端负责可视化、导出与快照。

核心原则：

- 只读数据库，使用只读账号，优先连接从库。
- 不修改 New API schema，不依赖不存在的导出接口。
- 服务端聚合，前端只展示。
- 不使用 Python、Redis。
- 缓存使用进程内 `lru-cache`，容量上限 1GB。
- 界面与新版 New API 保持一致的视觉体系。

|---|---|---|

| 部署 | Docker / Docker Compose | 独立部署 |

## 2. 数据库对接

### 2.1 连接方式

- 使用只读账号连接 PostgreSQL，优先连接只读从库。
- 连接池上限 10–20，每连接固定 `statement_timeout = 30s`、`default_transaction_read_only = on`。
- 连接串唯一来源为环境变量 `DATABASE_URL`。

```env
DATABASE_URL=postgres://dashboard_readonly:password@db-host:5432/new_api
```

只读账号：

```sql
CREATE ROLE dashboard_readonly LOGIN PASSWORD 'your_password';
GRANT CONNECT ON DATABASE new_api TO dashboard_readonly;
GRANT USAGE ON SCHEMA public TO dashboard_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dashboard_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO dashboard_readonly;
```

### 2.2 核心表

| 表 | 用途 | 特点 |
|---|---|---|
| `quota_data` | 按小时聚合的用量数据 | 适合天/周/月汇总；最多 5 分钟延迟；同键可能多行（维度含 token/channel/group） |
| `logs` | 原始消费日志 | 精确请求数、Token 输入/输出拆分、RPM |
| `users` | 用户基础信息 | 账号、昵称、状态、额度 |

字段以 `docs/db-schema-notes.md` §3 的实测结果为准：

- `quota_data`：`user_id`、`username`、`model_name`、`created_at`（Unix 秒）、`token_used`、`quota`、`count` 等 12 列；**无** `prompt_tokens` / `completion_tokens`。
- `logs`：`user_id`、`username`、`created_at`、`type`、`model_name`、`quota`、`prompt_tokens`、`completion_tokens` 等 21 列；`type = 2` 为消费流水。
- `users`：`id`、`username`、`display_name`、`status`、`quota`、`used_quota`、`request_count` 等 29 列。

### 2.3 保留策略

```sql
SELECT MIN(to_timestamp(created_at)), MAX(to_timestamp(created_at))
FROM quota_data;
```

实测两表覆盖约 97 天；超出保留期的数据不回补，接口与界面按实际区间返回。

### 2.4 索引建议

生产库是否建索引由 DBA 决策；从库只读，不能建索引。

```sql
CREATE INDEX CONCURRENTLY idx_quota_data_created_at ON quota_data (created_at);
CREATE INDEX CONCURRENTLY idx_quota_data_user_created ON quota_data (user_id, created_at);
CREATE INDEX CONCURRENTLY idx_quota_data_model_created ON quota_data (model_name, created_at);
CREATE INDEX CONCURRENTLY idx_logs_created_at ON logs (created_at);
CREATE INDEX CONCURRENTLY idx_logs_user_created ON logs (user_id, created_at);
```

实际库索引命名与列序不同，且缺少上述复合索引，详见 `docs/db-schema-notes.md` §3.4。

## 3. 统计维度

### 3.1 全局总览

- 总消耗额度、总请求数、总 Token（输入/输出/总计）。
- 活跃用户数、模型数量。
- 时间范围：今日、近 7 天、近 30 天、本月、自定义。

### 3.2 时间趋势

- 按天 / 周 / 月：消耗、请求数、Token、活跃用户。
- 每日消耗日历热力图。
- 环比（较上期）与同比（较去年同期）。

### 3.3 用户维度

- 用户消耗、请求数、Token 排行 Top N。
- 单用户详情：总览卡片、天/周/月趋势、模型消耗分布、Token 输入输出占比、活跃热力图、最近使用记录。
- 沉默用户：本期无消费、上期等长周期有消费的用户清单。

### 3.4 模型维度

- 模型消耗与请求数排行。
- 模型趋势。
- 用户 × 模型交叉分布。
- 单次请求平均成本。

### 3.5 渠道 / Token / 分组（可选）

按渠道、Token、分组统计消耗。

### 3.6 实时监控（可选）

最近 1 小时 RPM / TPM 与最近 24 小时请求趋势。实时指标取 `logs`，不使用有延迟的 `quota_data`。

## 4. API 设计

| 接口 | 说明 |
|---|---|
| `GET /api/overview` | 全局总览 |
| `GET /api/trend?granularity=day\|week\|month` | 全局趋势，支持 `compare=prev\|yoy` |
| `GET /api/users/ranking` | 用户排行 |
| `GET /api/users/inactive` | 沉默用户清单 |
| `GET /api/users/:id/overview` | 单用户总览 |
| `GET /api/users/:id/trend` | 单用户趋势 |
| `GET /api/users/:id/models` | 单用户模型分布 |
| `GET /api/models/ranking` | 模型排行 |
| `GET /api/models/trend` | 模型趋势 |
| `GET /api/models/cross` | 用户 × 模型交叉分布 |
| `GET /api/realtime/rpm` | 最近 RPM（可选） |
| `POST /api/snapshot` | 生成整页快照 |
| `GET /api/export/csv` | 导出 CSV |

统一查询参数：

- `start` / `end`：ISO 字符串或 Unix 秒，区间左闭右开。
- `granularity`：`day` / `week` / `month`。
- `userId` / `modelName` / `limit`。

## 5. 核心 SQL

### 5.0 统一口径

所有 `logs` / `quota_data` 聚合必须满足：

- `logs` 仅统计消费流水：`type = 2`。
- 排除管理员账号 `admin`（按 `users.id` 解析，用户名兜底）。
- 聚合结果显式 `::bigint`，避免 `numeric` 被驱动解析为字符串。

```sql
-- 管理员排除条件，追加到各查询的 WHERE
(coalesce(lower(username), '') <> 'admin')
AND (
  user_id IS NULL
  OR user_id NOT IN (SELECT id FROM users WHERE lower(username) = 'admin')
)
```

以下 SQL 省略该条件。

### 5.1 全局总览

```sql
-- 额度 / Token 总量 / 活跃用户 / 模型数
SELECT
  COALESCE(SUM(quota), 0)::bigint       AS total_quota,
  COALESCE(SUM(token_used), 0)::bigint  AS total_tokens,
  COUNT(DISTINCT user_id)::bigint       AS active_users,
  COUNT(DISTINCT model_name)::bigint    AS model_count
FROM quota_data
WHERE created_at >= $1 AND created_at < $2;

-- 请求数与 Token 拆分（logs）
SELECT
  COUNT(*)::bigint                                AS request_count,
  COALESCE(SUM(prompt_tokens), 0)::bigint         AS prompt_tokens,
  COALESCE(SUM(completion_tokens), 0)::bigint     AS completion_tokens
FROM logs
WHERE type = 2 AND created_at >= $1 AND created_at < $2;
```

Token 总量取 `max(quota_data.token_used, prompt_tokens + completion_tokens)`，兼容两张表最多 5 分钟的延迟差。

### 5.2 按天趋势

```sql
SELECT
  DATE_TRUNC('day', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS day,
  SUM(quota)::bigint      AS total_quota,
  SUM(token_used)::bigint AS total_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY 1
ORDER BY 1;
```

### 5.3 按周趋势

```sql
SELECT
  DATE_TRUNC('week', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS week,
  SUM(quota)::bigint      AS total_quota,
  SUM(token_used)::bigint AS total_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY 1
ORDER BY 1;
```

### 5.4 按月趋势

```sql
SELECT
  DATE_TRUNC('month', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS month,
  SUM(quota)::bigint      AS total_quota,
  SUM(token_used)::bigint AS total_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY 1
ORDER BY 1;
```

### 5.5 单用户按天趋势

```sql
SELECT
  DATE_TRUNC('day', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS day,
  SUM(quota)::bigint      AS total_quota,
  SUM(token_used)::bigint AS total_tokens
FROM quota_data
WHERE user_id = $1
  AND created_at >= $2 AND created_at < $3
GROUP BY 1
ORDER BY 1;
```

### 5.6 单用户模型分布

```sql
-- 额度与 Token 总量
SELECT
  model_name,
  SUM(quota)::bigint      AS total_quota,
  SUM(token_used)::bigint AS total_tokens
FROM quota_data
WHERE user_id = $1
  AND created_at >= $2 AND created_at < $3
GROUP BY model_name
ORDER BY total_quota DESC;

-- Token 输入/输出拆分（logs）
SELECT
  model_name,
  SUM(prompt_tokens)::bigint     AS prompt_tokens,
  SUM(completion_tokens)::bigint AS completion_tokens
FROM logs
WHERE type = 2
  AND user_id = $1
  AND created_at >= $2 AND created_at < $3
GROUP BY model_name;
```

### 5.7 用户消耗排行

```sql
SELECT
  user_id,
  SUM(quota)::bigint      AS total_quota,
  SUM(token_used)::bigint AS total_tokens
FROM quota_data
WHERE created_at >= $1 AND created_at < $2
GROUP BY user_id
ORDER BY total_quota DESC
LIMIT $3;
```

用户名与昵称按 `user_id` 从 `users` 表补齐；请求数按 `user_id` 聚合 `logs`。

### 5.8 最近 1 小时 RPM

```sql
SELECT
  DATE_TRUNC('minute', to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai') AS minute,
  COUNT(*)::bigint AS requests
FROM logs
WHERE type = 2
  AND created_at >= EXTRACT(EPOCH FROM NOW())::bigint - 3600
GROUP BY 1
ORDER BY 1;
```

## 6. 缓存方案

### 6.1 选型

进程内 `lru-cache`，不引入 Redis。容量上限 1GB，核心风险为慢泄漏。

### 6.2 配置

```ts
import { LRUCache } from "lru-cache";

const cache = new LRUCache<string, unknown>({
  maxSize: 1024 * 1024 * 1024,
  ttlAutopurge: true,
  updateAgeOnGet: false,
  sizeCalculation: (value) => Buffer.byteLength(JSON.stringify(value), "utf8"),
  dispose: (_value, key, reason) => {
    if (process.env.NODE_ENV !== "production") {
      console.debug(`[cache] evict ${key} reason=${reason}`);
    }
  },
});
```

### 6.3 防慢泄漏措施

1. **强制 TTL**：每条缓存必须设置 TTL，禁止 `ttl: 0`；`ttlAutopurge: true`；`updateAgeOnGet: false`。
2. **控制 key 数量**：key 由查询参数确定性生成，时间戳取整到秒；`modelName` 等输入做白名单与长度限制。
3. **分级 TTL**：

   | 数据 | TTL |
   |---|---|
   | 全局总览 | 60s |
   | 用户排行 / 沉默用户 | 120s |
   | 单用户趋势 | 30s |
   | 模型分布 | 30s |
   | 实时 RPM | 10s |
   | 历史月度汇总 | 1h |

4. **监控**：每 5 分钟输出 `size` / `calculatedSize` / `maxSize`；长期接近上限即视为异常。
5. **兜底清理**：SIGTERM 清空缓存；提供受保护的 `/api/admin/cache/clear` 手动清理。

### 6.4 内存评估

缓存内容为聚合结果而非原始日志：单序列约 0.2–0.5 KB，用户排行 Top 100 约 30 KB，单用户详情约 50–200 KB。1GB 上限有充足余量；长期逼近上限应排查 key 生成与 TTL，而非扩容。

### 6.5 不缓存场景

单次聚合在合理索引下耗时 < 100ms 时直接查询，优先用 SQL 与索引替代缓存。

## 8. 静态 HTML 快照导出

### 8.1 前端单图导出

自包含 HTML 模板：序列化 `chart.getOption()`，内联 ECharts 运行时，不依赖外部 CDN。

```ts
const html = renderSingleChartHtml({
  title: "user-report",
  option: chart.getOption(),
  echartsSource,
});
```

导出文件保留 tooltip、图例筛选与缩放；主题按当前页面内联。

### 8.2 服务端整页快照

Playwright 渲染受保护页面并保存 HTML：

```ts
const browser = await chromium.launch();
const context = await browser.newContext({ extraHTTPHeaders: { cookie } });
const page = await context.newPage();
await page.goto(`${baseUrl}/users/123?start=...&end=...`);
await page.waitForLoadState("networkidle");
const html = await page.content();
```

- 产物写入 `SNAPSHOT_DIR`（默认 `data/snapshots`），不放入 `public/`。
- 读取经受登录保护的 `GET /api/snapshots/[file]`，文件名为白名单校验，禁止路径穿越。

### 8.3 快照内容

全局总览、单用户报告、月度报表、模型分析报告。

## 9. 安全与性能

### 9.1 数据库安全

- 只读账号，优先从库。
- 参数化查询，禁止拼接 SQL；Kysely 提供类型约束。
- 会话固定只读事务与 `statement_timeout = 30s`。

### 9.2 查询性能

- 合理索引；大范围查询前先评估执行计划。
- API 层使用 Zod 校验参数。
- 导出接口按 IP 限流。

### 9.3 缓存安全

- key 规范化，避免无限增长。
- 监控 `size` 与 `calculatedSize`。
- 提供手动清理端点，访问受 `ADMIN_TOKEN` 保护。

## 11. 部署

### 11.1 Docker Compose

```yaml
services:
  dashboard:
    build: .
    ports:
      - "3088:3088"
    environment:
      DATABASE_URL: postgres://dashboard_readonly:password@db-host:5432/new_api
      TZ: Asia/Shanghai
      DASHBOARD_BASE_URL: http://localhost:3088
    restart: unless-stopped
```

容器内 `PORT=3088`，健康检查 `GET /api/health`。

### 11.2 访问控制

- 独立登录页 + HttpOnly 会话 Cookie（HMAC-SHA256 签名，12h）。
- 页面未登录重定向 `/login`，接口返回 401；凭据缺失时生产环境拒绝启动。
- 快照目录不在 `public/`，读取经受保护路由。
