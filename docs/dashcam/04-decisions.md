# 决策记录

记录已做出的取舍与否决方案。每条包含结论、依据与代价；只写结论，不保留讨论过程。

## D1 不 fork New API，采集点放在进程外

**结论**：不修改 New API 源码，不重建其镜像。

**依据**：改动量虽小（在消费日志写入处补一个 `other.SetAdmin("prompt", …)`），但需要分叉仓库并长期跟随上游 rebase。写入点所在的 relay 与日志模型代码在上游持续重构，补丁冲突概率高。

**代价**：采集逻辑无法复用 New API 的权限模型（`admin_info` 的管理员可见投影），后台日志详情页看不到提问内容，必须在看板另做界面。

上游存在同诉求 issue（[#7609](https://github.com/QuantumNous/new-api/issues/7609)），如后续官方实现，应评估切换到原生能力并停用本组件。

## D2 不使用 nginx `mirror` 旁路

**结论**：否决。

**依据**：`mirror` 复制的是请求，响应只有主请求一份。方案只满足“存提示词”，不满足“存返回内容”，而后者是本次需求的必要条件。

**代价**：采集组件进入转发路径，引入可用性变量（用 D4 的 failover 缓解）。

## D3 不使用 nginx Lua 采集

**结论**：否决，尽管目标机已编译 `lua-nginx-module 0.10.29` 与 `ngx_devel_kit`。

**依据**：五处硬伤，每处都需要自行填补：

| 问题 | 说明 |
|---|---|
| 请求体读取 | `ngx.req.get_body_data()` 仅在 body 位于内存缓冲时有效；超过 `client_body_buffer_size` 后需 `get_body_file()` + `io.open`，而 Lua 文件 IO 会**阻塞 worker** |
| 响应体读取 | `body_filter_by_lua` 阶段 **cosocket 被禁用**，必须靠 `ngx.timer.at` 延迟投递 |
| 压缩干扰 | 上游若返回 gzip，`body_filter` 拿到的是二进制块，需额外强制 `Accept-Encoding: ""` 或引入 zlib |
| 缺少基础库 | 目标机无 `lua-resty-http`，`lua-cjson` 需另行确认；HTTP 客户端与 JSON 序列化都要手写 |
| 数据丢失 | worker reload 会丢弃在途 timer，静默丢采集且难以观测 |

**代价**：多一个容器或进程（约 6.6 MB 二进制）。相对于上述实现风险，这个代价可接受。

## D4 前置代理不嵌入看板进程

**结论**：代理独立进程，独立发布。

**依据**：

1. 嵌入 Next.js 会让看板成为业务关键路径——看板不可用等于全公司 LLM 调用中断。
2. 代理是协议级工作：逐跳头剥离、`Content-Length` 与 chunked 冲突、`duplex: "half"`、客户端断开的 abort 传播、`X-Accel-Buffering`、Upgrade 无法 hijack。这些 `httputil.ReverseProxy` 已全部覆盖，Route Handler 需逐项自行实现。

**代价**：多一个部署单元。通过同仓库、同 compose、共享目录把运维成本压到最低。

## D5 采集产物存文件，不建表

**结论**：落本地文件，不写 PostgreSQL。

**依据**：

1. 看板对数据库是只读的（类型层无写入口、会话强制只读事务）。要写入必须开一条完全独立的写通道，触及架构红线。
2. 需求是点查（某用户某次会话的内容），不是聚合分析；文件完全够用。
3. 无 DDL、无写账号、无迁移，回滚不涉及数据层。

**代价**：无法做 SQL 聚合与全文检索；文件数随时间膨胀，必须配清理策略（见 [03-deployment.md](03-deployment.md) §7）。

## D6 目录按调用方指纹分组，不用 user_id

**结论**：`sha256(Authorization)[:12]` 作为二级目录名。

**依据**：New API 不透传用户身份，代理只能看到 `sk-...`。三条替代路径均不可接受：代理连库（破坏零依赖）、代理拉管理接口（引入凭据与故障路径）、请求头注入（需改 New API）。

**代价**：看板读取时需多一次指纹 → token → user 的映射；指纹与用户是多对一关系，聚合时要在读取层完成。

## D7 上限 128 MiB，边转发边写盘

**结论**：请求/响应各 128 MiB 落盘上限；实现用 `io.TeeReader` 而非整体读入。

**依据**：1M tokens 上下文约 4–5 MB 原始 JSON，多模态场景可达数十 MB。整体读入会让内存随 body 线性增长，并发即内存爆炸。Tee 方式内存恒定（每请求约 64 KiB 缓冲），上限因此只用于防磁盘失控。

**代价**：写入发生在转发过程中，磁盘慢会延迟采集完成时间（但不影响转发）；客户端断开时文件可能只写一半，用索引 `tr` 位标识。

## D8 代理不做协议归一化，归一化放在看板读取侧

**结论**：代理只做"透传 + 原样落盘 + 极轻量提取"——提取范围限定为**从请求 peek 的正则匹配**（模型名、流式标记、会话键）与**响应尾部的 usage 对象**（D11），不做消息块解析与协议归一化；后者用 TypeScript 在看板实现。

**依据**：

- 代理代码面压到最小，出错概率低，且它是关键路径组件。
- 采集与展示的共享契约只剩"目录结构 + 文件名 + 截断上限 + 索引字段"几条，看板改解析规则不需要重新编译代理。
- 解析逻辑演进频繁，Go 侧改动成本高于 TS 侧。

**代价**：看板需实现 SSE 与四种协议的解析；落盘体积含协议包装（SSE 约放大 30–40 倍），由 gzip 与截断控制。

## D11 token 用量在采集端提取并写入索引

**结论**：代理在落索引前对响应正文做 best-effort usage 提取（尾部 8MB 窗口扫描 `"usage":{...}` 对象，按字段合并兼容四种协议），写入索引 `pt/ct/cc/cw`；看板以索引字段为唯一权威来源展示 token，正文解析仅作旧数据回退。

**依据**：

- 索引原本没有 token，看板列表只能读正文水合（每页最多 100 个文件）或显示请求体字节（诊断价值低）；采集时正文恰好完整经过代理，零额外读取。
- 提取是尾部子串扫描 + 少量小 JSON 解析（毫秒级），规避了"代理全量解析 JSON"的 D8 红线——正文字符串值里的 `"usage"` 因 JSON 转义不会误命中。
- 按字段合并且取最后非零值，天然覆盖 Anthropic 流（input/cache 在 `message_start`、output 在 `message_delta`）与 OpenAI 流（usage 在最后 chunk）。

**代价**：

- 索引行增加四个可选字段（约 +50 B/行，按当前规模 +25% 索引体积）。
- usage 字段名解析在 Go 与 TS 两侧各有一份实现，存在漂移风险——以共享契约样例（`dashcam/testdata/usage/`）+ 双侧测试锁死，契约测试已实际抓到并修复 TS 侧丢失 Anthropic `cache_creation_input_tokens` 的偏差。
- 截断的响应可能丢失尾部 usage（省略字段，显示 `—`）；超 8MB 的超长流里更早出现的 usage（如 Anthropic `message_start`）会缺失，属刻意接受的内存上界取舍。

## D9 代码同仓库，发布流水线独立

**结论**：`dashcam/` 放在看板仓库内，但用独立 tag（`dashcam-v*`）与独立 workflow 发布。

**依据**：共享契约极薄（D8），跨仓库的协调成本大于收益。但代理处于关键路径，不能因为改前端代码就跟着重启，因此发布必须解耦。

**代价**：仓库内存在 Go 与 Node 两套工具链，需要在 `.dockerignore`、`.gitignore`、`eslint` 中显式排除，避免互相污染。

## D10 采集路径白名单，只收对话接口

**结论**：仅 `/v1/chat/completions`、`/v1/completions`、`/v1/messages`、`/v1/responses` 落盘，其余路径直接放行。

**依据**：图片生成接口的 `b64_json`、音频与文件接口的二进制体，单次请求即可写数百 MB，且无内容追溯价值。

**代价**：新增协议（如 embedding、rerank、自定义任务接口）需显式加入白名单，否则静默不采集。白名单是配置项，无需重新编译。
