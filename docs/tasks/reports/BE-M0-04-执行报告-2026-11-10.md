## 4. 关键结论与踩坑

1. **`cache.purge()` 不存在**：方案 §6.3(5) 示例写 `cache.purge()`，lru-cache v11 只有 `clear()`/`purgeStale()`。按语义等价实现 `clear()`，未改方案（建议回流措辞，见下）。
2. **`cacheComponents` 预渲染陷阱（本次实测发现）**：`next build` 初次把 `/api/admin/cache/stats` 标记为 ○（静态），构建期以无 `ADMIN_TOKEN` 执行了一次 GET，会把 404 固化成静态响应；且 `export const dynamic` 与 `cacheComponents` 不兼容直接构建失败。修复：端点内 `await connection()` 转请求期动态，构建标记变 ƒ，生产 e2e 两种 token 状态均正确。
3. **lru-cache v11 类型约束**：`LRUCache<K, V>` 要求 `V extends {}`，不能用 `unknown`；缓存值类型定为 `object | string | number | boolean`。
4. **TTL 单测的时钟注入**：lru-cache 会把 `perf.now()` 结果缓存 `ttlResolution`（默认 1ms），同步推进注入时钟时第二次 `get` 仍读旧值；单测实例用 `ttlResolution: 0` + 注入 `perf` 保证确定性，不 sleep。
5. **Windows 无真实 SIGTERM**：以单测直接调用注册监听器验证行为；Linux 生产由 `process.once` 生效。
