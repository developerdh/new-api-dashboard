## 本任务关键口径摘要
- 实例配置按 §6.2：`maxSize: 1024*1024*1024`、`ttlAutopurge: true`、`updateAgeOnGet: false`、`sizeCalculation = Buffer.byteLength(JSON.stringify(value))`、dev 环境 dispose 淘汰日志。
- 分级 TTL 常量表（§6.3(3)）：overview 60s、usersRanking 120s、userTrend 30s、modelDist 30s、realtime 10s（预留）、historyMonth 3600s。
- key 规范（§6.3(2)）：`cacheKey(scope, params)` 确定性生成，参数按固定顺序 `${scope}:${granularity}:${start}:${end}:${userId ?? 'all'}:${modelName ?? 'all'}`；时间戳取整到秒；字符串参数白名单正则 + 长度 ≤128 校验，非法即抛错（防 key 无限增长）。
- `getOrCache(key, ttlMs, fn)`：命中直返；未命中执行 fn 并写缓存；异常不写缓存（防污染）。
- 监控（§6.3(4)）：每 5 分钟 `console.log('[cache]', {size, calculatedSize, maxSize})`；定时器 `unref()`。
- 兜底（§6.3(5)）：`SIGTERM` 时清空缓存（挂 `src/instrumentation.ts` register）；`POST /api/admin/cache/clear`：`Authorization: Bearer ${ADMIN_TOKEN}`（env 未设置时端点返回 404，禁用优先）；`GET /api/admin/cache/stats` 同守卫。
- dev 热重载：实例挂 globalThis 单例（同 BE-M0-02 模式）。
- 实现结论（本卡落地）：lru-cache v11 已无 `purge()`，SIGTERM/清理统一用 `clear()`（语义等价，不改方案）；Next 16 `cacheComponents: true` 下管理端点 GET 会被预渲染，必须用 `connection()` 转请求期动态（`export const dynamic` 与之不兼容）；守卫用 SHA-256 摘要 + `timingSafeEqual` 比较。

## 风险/阻塞
- Windows 无真实 SIGTERM 交付语义：handler 以单测「直接调用已注册监听器」验证清空行为；Linux 生产按 `process.once` 生效。
- `cacheComponents: true` 的预渲染陷阱：管理端点 GET 若无 `connection()` 会被构建期执行并静态化（实测会把 404 固化成静态响应）；新增管理端点必须复用 `connection()` 写法。
- 单条结果体量：无真实数据，未实测 >1MB 的聚合结果；`maxEntrySize` 默认等于 `maxSize`（1GB），超限单条不写入（有单测覆盖，用小 maxSize 模拟）。
